Designing for under 10 ms end to end

A latency budget is a design document. Here is how to write one before the first line of code.

When a system has to process a message in under ten milliseconds, from the moment it arrives to the moment the result is available, you cannot fix latency later. You have to spend it deliberately, hop by hop, the way you would spend a financial budget.

Start with the budget, not the architecture

List every hop a message takes: network in, deserialization, validation, the business rule, persistence or publish, network out. Give each hop a number. The numbers will be wrong, and that is the point. The first measurement shows which assumption to challenge.

Keep the hot path boring

Anything that allocates, blocks or calls out belongs off the hot path. If a step can be done before the message arrives, or after the answer has left, move it there. What remains should be small enough to reason about in your head.

Throughput is what you promise on an average day. Latency is what you promise on the worst one.

Measure percentiles, not averages

At 100,000 messages per second, one slow message in a thousand is a hundred slow messages every second. Track p99 and p99.9 for each hop, and alert on the budget, not on the average.
